# Swarm Configuration Mappings

This file maps configuration axes to concrete Swarm behavior.

## Team Shape

- Higher `rigor / stakes` -> more critics, stronger skeptical roles.
- Higher `creativity need` -> more evangelist energy, more route-generators.
- High `rigor` + high `grounding` -> prefer concrete expert archetypes over airy personas.
- High `creativity` + lower `grounding` -> abstract or composite personas are more acceptable.

## Recommended Team Size

- Mostly `low` / `medium` axes and narrow scope -> `3-4` experts.
- Substantial default full swarm -> `5` experts.
- High `rigor / stakes` or high `problem ambiguity` with meaningful route branching -> `5-7` experts.
- Do not scale team size up unless the extra roles create real route discrimination.

## Critic / Evangelist Balance

- Baseline full swarm: at least `2 critics` and at least `1 evangelist`.
- `high rigor / stakes` + `high grounding need` -> increase critic share.
- `high creativity need` + `wide branching budget` -> increase evangelist share.
- Mixed tasks often want a `2 critics / 1 evangelist / 2 balanced` default at team size 5.
- If a task is highly asymmetric, record that explicitly rather than silently drifting from the default topology.

## Phase 1 Intensity

- Higher `problem ambiguity` -> stronger problem framing, clearer non-goals, more explicit assumptions.
- Lower `problem ambiguity` -> leaner Phase 1 is acceptable.

## Grounding Bias

- Higher `grounding need` -> use `E` earlier and more often.
- Lower `grounding need` -> exploratory rounds can precede tool-backed discrimination.

## Recommended Grounding Posture

- `high grounding need` -> default to tool-backed discrimination whenever practical.
- `medium grounding need` -> allow one exploratory round before grounding if it improves route selection.
- `low grounding need` -> grounding can be deferred until it becomes a useful discriminator rather than an opening move.

## Route Management

- Wider `route branching budget` -> more exploration before compression.
- Narrower `route branching budget` -> faster movement to `C`, `D`, or `E`.

## Planning / Branching Posture

- `narrow` branching budget -> aggressive pruning, faster movement to `C`, `D`, and `E`.
- `moderate` branching budget -> explore, then compress once one or two routes start dominating.
- `wide` branching budget -> tolerate multiple live routes longer, but keep route labels explicit to avoid drift.

Use `X` only when the task needs adversarial cross-examination or burden-of-proof testing; it is not part of the default branching ladder.

## Closure Behavior

- Higher `closure strictness` -> stronger `G`, harder `H`, more visible unresolved risks.
- Lower `closure strictness` -> pragmatic recommendation with bounded caveats may be enough.

## Recommended Closure Threshold

- `high closure strictness` -> strong checkpoint scrutiny, explicit remaining uncertainty, and readiness to say the answer was not found.
- `medium closure strictness` -> practical recommendation is acceptable if key uncertainties are bounded.
- `low closure strictness` -> useful directional synthesis may be enough even if several uncertainties remain open.

## Persona Guidance

Decide whether to use:
- concrete real named experts,
- abstract role labels,
- or composite archetypes.

Prefer:
- real named experts when authority style or intellectual lineage is useful and the task is grounded enough to benefit,
- abstract roles when precision matters more than performative persona,
- composite archetypes when the task is exploratory and no single real figure is the right fit.

Do not use named personas just for flavor.
